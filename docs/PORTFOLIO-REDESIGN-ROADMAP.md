# Portfolio Redesign Roadmap

> الحالة: خطة معتمدة للفكرة ولم يبدأ تنفيذ إعادة التصميم بعد.
>
> الهدف: إعادة بناء تجربة البورتفوليو بصرياً ووظيفياً بحيث تصبح المشاريع والمهارات هي مركز الموقع، مع Hero شخصي قوي وصورة احترافية، وتحويل عرض المشاريع من وصف ثابت إلى تجارب تفاعلية مصغرة تحاكي المنتجات الحقيقية.

## 1. المبادئ العامة

- عدم الالتزام بالستايل الحالي؛ إعادة تقييم الهوية البصرية كاملة قبل تنفيذ الواجهات الجديدة.
- المشاريع هي أهم جزء في الموقع ويجب أن تحصل على المساحة والاهتمام الأكبر.
- المهارات تأتي مباشرة بعد المشاريع ويجب عرضها بطريقة توضح القدرة العملية، لا كقائمة نصية عادية فقط.
- إضافة صورة شخصية احترافية في أول جزء من الموقع لتقوية الهوية والثقة والحضور الشخصي.
- الحفاظ على الموقع سريعاً وخفيفاً ومتجاوباً على الهاتف والتابلت والديسكتوب.
- الحفاظ على العربية والإنكليزية ودعم RTL/LTR بشكل صحيح.
- عدم استخدام معلومات أو صور أو ميزات وهمية على أنها حقيقية. أي بيانات داخل الـDemo تكون واضحة بأنها تجريبية.

## 2. الأولوية الأولى — Hero جديد مع صورة شخصية

### الهدف

يكون أول انطباع في الموقع شخصي واحترافي، وليس واجهة تقنية مجردة فقط.

### المطلوب

- وضع صورة حيدره بشكل بارز في الـHero.
- إنشاء صورة احترافية مخصصة للموقع اعتماداً على صورة حقيقية يزودنا بها حيدره لاحقاً.
- الصورة يجب أن تكون شديدة الوضوح، نظيفة، طبيعية، وتناسب هوية مطور برمجيات حديثة بدون مبالغة أو مظهر Stock.
- تجهيز أكثر من Crop للصورة حتى تعمل جيداً على الشاشات المختلفة.
- يفضل تجهيز النسخ النهائية بصيغ WebP/AVIF مع نسخة أصلية عالية الدقة.
- تحديد اتجاه بصري متناسق بين الصورة والخلفية والنص والأزرار، وليس وضع الصورة كعنصر منفصل فقط.

### مواصفات مقترحة للصورة

- Portrait احترافي Editorial / Tech.
- إضاءة نظيفة وتفاصيل وجه واضحة جداً.
- خلفية بسيطة أو بيئة حديثة هادئة لا تنافس المحتوى.
- ألوان قابلة للاندماج مع الستايل النهائي للموقع.
- دقة أصلية عالية تكفي للشاشات Retina.
- لا يتم توليد الصورة النهائية قبل توفير صورة مرجعية واضحة لحيدره.

## 3. الأولوية الثانية — إعادة تصميم قسم المشاريع بالكامل

### المشكلة الحالية

عرض المشاريع الحالي لا يعطي المشاريع وزنها الحقيقي، ولا يسمح للزائر بفهم المنتج أو تجربته بسرعة.

### الاتجاه الجديد

تحويل كل مشروع إلى Product Showcase واضح يتكون من:

- اسم المشروع وهوية بصرية قوية.
- وصف مختصر جداً ومباشر.
- نوع المشروع أو المشكلة التي يحلها.
- أهم التقنيات عند الحاجة.
- Visual Preview قوي.
- زر واضح لتفاصيل المشروع.
- زر أساسي: **جرّب المشروع** عند توفر Demo تفاعلي.

### مبدأ مهم

الـPortfolio نفسه له هوية واحدة، لكن عند فتح تجربة مشروع، يجب أن تدخل التجربة إلى هوية ذلك المشروع نفسه:

- نفس ألوان المشروع الحقيقي.
- نفس روح الـUI والـComponents.
- نفس اتجاه التصميم العام.
- ليست نسخة Pixel-perfect من المشروع الحقيقي.
- هي محاكاة مبسطة تحافظ على شخصيته وتشرح أهم Workflow.

## 4. Interactive Project Demos

### الفكرة

إنشاء Demo مصغر لكل مشروع يسمح للزائر بالنقر والتفاعل بدلاً من الاكتفاء بالصور والوصف.

الـDemo ليس نسخة كاملة من التطبيق ولا يحتاج Backend حقيقي. الهدف أن يفهم الزائر جوهر المشروع خلال تقريباً 30–90 ثانية.

### الهيكل المقترح

```text
demos/
├── enterprise-workflow/
│   ├── index.html
│   ├── demo.css
│   └── demo.js
├── coding-academy/
├── mahsoob/
└── masroofi/
```

يمكن تعديل الهيكل لاحقاً حسب الستايل الجديد، لكن يجب أن تبقى كل تجربة معزولة بصرياً حتى لا تتعارض Styles المشاريع مع البورتفوليو أو مع بعضها.

### قواعد مشتركة لكل Demo

- بيانات تجريبية جاهزة عند الفتح، حتى لا تكون الواجهة فارغة.
- زر **Reset Demo** يعيد التجربة للحالة الأولية.
- لا تسجيل دخول حقيقي.
- لا Backend ضروري في البداية.
- الحالة التفاعلية يمكن إدارتها داخل JavaScript / browser state.
- توضيح أن البيانات Demo وليست بيانات حقيقية.
- دعم Keyboard وFocus states بقدر مناسب.
- Responsive على الهاتف والديسكتوب.
- الحفاظ على سرعة التحميل.

## 5. Role Switching للمشاريع متعددة المستخدمين

### الهدف

إظهار الـWorkflow الحقيقي للمشروع من وجهات نظر مستخدمين مختلفين بدون الحاجة لعدة حسابات.

### العنصر المقترح

زر أو Dropdown واضح داخل الـDemo مثل:

```text
👤 الموظف ▾
```

والأدوار الممكنة تظهر حسب المشروع، مثلاً:

```text
👤 موظف
👔 مدير
🛡️ Admin
```

### السلوك

تغيير الدور يجب أن يغير فعلياً:

- الشاشة أو Dashboard المعروضة.
- العناصر التي يراها المستخدم.
- الإجراءات المتاحة.
- حالة الطلبات أو المهام المناسبة لذلك الدور.

لا يكون مجرد تغيير اسم الدور في الهيدر.

## 6. سيناريوهات Demo المقترحة لكل مشروع

### Enterprise Workflow

أقوى مشروع للاستفادة من Role Switching.

Flow مقترح:

1. الدخول كموظف.
2. إنشاء طلب جديد.
3. إرسال الطلب.
4. تبديل الدور إلى المدير.
5. ظهور الطلب ضمن الطلبات الواردة.
6. فتح الطلب.
7. الموافقة عليه أو إرجاعه.
8. الرجوع إلى دور الموظف.
9. مشاهدة حالة الطلب الجديدة.

يمكن لاحقاً إضافة أدوار أخرى فقط إذا كانت تضيف قيمة واضحة للتجربة.

### محسوب — مشروع الكاشير

Flow مقترح:

1. اختيار / إضافة منتجات للسلة.
2. تغيير الكمية أو حذف منتج.
3. تحديث Subtotal والإجمالي فورياً.
4. تنفيذ عملية دفع تجريبية.
5. عرض فاتورة مصغرة أو نجاح العملية.

إذا كان المشروع الحقيقي يحتوي دور إداري مهم، يمكن إضافة تبديل إلى Admin لعرض مثال سريع لإدارة المنتجات أو المبيعات.

### مصروفي — المصاريف الشخصية

Flow مقترح:

1. إضافة عملية صرف تجريبية.
2. اختيار التصنيف والقيمة والتاريخ.
3. تحديث إجمالي الصرف والمؤشرات مباشرة.
4. تحديث Chart أو Summary بصري.
5. تعديل أو حذف العملية.

يمكن لاحقاً تمثيل ميزات مثل المقارنة الشهرية والمتوسط اليومي/الأسبوعي إذا أصبحت جزءاً فعلياً من المنتج.

### أكاديمية البرمجة

Flow مقترح:

1. فتح مسار تعليمي.
2. اختيار درس.
3. إكمال نشاط أو مثال صغير.
4. تحديث Progress.
5. فتح الدرس التالي أو ظهور إنجاز بسيط.

## 7. الأولوية الثالثة — إعادة تصميم عرض المهارات

### المشكلة الحالية

قائمة المهارات النصية لا توضح مستوى القدرة ولا تربط المهارة بالأعمال الفعلية.

### الاتجاه الجديد

استبدال القائمة البسيطة بتجربة بصرية أوضح، مثل مجموعة Categories / Capability Cards مرتبطة بما تم تنفيذه فعلياً.

أمثلة فئات ممكنة:

- Backend Development
- System Design & Architecture
- Databases
- Testing & Quality
- Git / GitHub Workflow
- AI-assisted Development
- Debugging & Problem Solving
- Deployment / Release Readiness

### طريقة العرض المطلوبة

كل Skill/Capability يفضل أن يحتوي واحداً أو أكثر من:

- اسم واضح.
- شرح قصير لما يمكن تنفيذه بهذه المهارة.
- أدوات أو تقنيات مرتبطة بها.
- مشروع أو Proof مرتبط بها عند توفره.

الهدف أن يجيب القسم على سؤال: **ماذا يستطيع هذا المطور أن يبني أو يحل؟** وليس فقط: **ما أسماء الأدوات التي يعرفها؟**

## 8. ترتيب العمل المقترح

### Phase 1 — Discovery & Visual Direction

- مراجعة الستايل الحالي وتحديد ما سيتم الاحتفاظ به وما سيتم حذفه.
- جمع Inspiration وReferences.
- تحديد شخصية البورتفوليو الجديدة: Typography، Colors، spacing، motion، cards، navigation.
- تحديد شكل Hero والصورة الشخصية.
- عمل Wireframe سريع لأهم أجزاء الصفحة.

### Phase 2 — Hero + Core Layout

- بناء Hero الجديد.
- إضافة الصورة الشخصية بعد تجهيزها.
- إعادة ضبط Grid والمسافات والنظام البصري العام.
- تثبيت responsive foundations.

### Phase 3 — Projects Showcase

- إعادة بناء بطاقات/أقسام المشاريع.
- تجهيز مكان واضح لمحسوب ومصروفي.
- تحسين Enterprise Workflow وأكاديمية البرمجة ضمن نفس النظام.
- إضافة CTA للتجارب التفاعلية.

### Phase 4 — Skills / Capabilities

- بناء العرض الجديد للمهارات.
- ربط المهارات بالمشاريع والأدلة العملية عند توفرها.

### Phase 5 — Interactive Demos

- Enterprise Workflow أولاً لأنه يثبت فكرة Role Switching.
- محسوب.
- مصروفي.
- أكاديمية البرمجة.

### Phase 6 — Polish

- Motion خفيف ومدروس.
- Accessibility.
- Keyboard interactions.
- Performance optimization.
- تحسين الصور.
- مراجعة Mobile/Tablet/Desktop.
- مراجعة العربية والإنكليزية.

## 9. قرارات مهمة قبل بدء التنفيذ

قبل كتابة إعادة التصميم الفعلية يجب حسم التالي:

- الاتجاه البصري النهائي للموقع.
- شكل الـHero وحجم حضور الصورة.
- هل عرض المشاريع Full-width sections أم Cards أم Hybrid.
- كيف تفتح الـDemo: صفحة مستقلة أم Overlay/Fullscreen experience.
- ما هي أهم Flow واحدة أو اثنتين لكل مشروع.
- ألوان وهوية كل مشروع من الواجهة الحقيقية.
- الصور والـScreenshots المرجعية المعتمدة لكل مشروع.

## 10. Definition of Done لإعادة التصميم

تعتبر المرحلة الجديدة ناجحة عندما:

- أول شاشة توضح بسرعة من هو حيدره وماذا يبني.
- الصورة الشخصية جزء قوي وطبيعي من الهوية.
- المشاريع هي العنصر الأبرز في الصفحة.
- الزائر يستطيع فهم كل مشروع بسرعة بدون قراءة نص طويل.
- المشاريع المناسبة تمتلك Demo تفاعلي قابل للنقر.
- المشاريع متعددة الأدوار تسمح بتبديل الأدوار وفهم الـWorkflow.
- كل Demo يحافظ على ألوان وتصميم وهوية المشروع الحقيقي.
- قسم المهارات يوضح القدرات العملية وليس أسماء تقنيات فقط.
- الموقع ممتاز بصرياً على الهاتف والديسكتوب.
- الأداء يبقى سريعاً رغم الصور والتفاعلات.

## 11. ملاحظات تنفيذية حالية

- تمت إضافة أماكن أولية لمشروعي **محسوب** و**مصروفي** على فرع العمل الحالي، لكنها ليست التصميم النهائي.
- هذه الـplaceholders قابلة للإزالة أو إعادة البناء بالكامل عندما يبدأ الـRedesign.
- لا يجب بناء تفاصيل كثيرة فوق الستايل الحالي لأن الاتجاه العام للموقع سيعاد تصميمه.
- الأولوية القادمة عند بدء التنفيذ هي Visual Direction وليس زيادة تعديلات تجميلية على التصميم الحالي.
